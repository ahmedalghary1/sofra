# خطة التنفيذ والحالة

المرجع هو ملف المواصفات الأصلي في الجذر. التطبيق قابل للتجربة، لكنه لم يحقق جميع قصص المستخدم أو شروط الإطلاق التجاري.

| المجال | الحالة | التفاصيل |
|---|---|---|
| الأساس والحسابات والعزل | جزئي | تسجيل ودخول واستعادة كلمة المرور، فروع وعضويات وأدوار وتعطيل الموظف واختبارات عزل؛ لوحة إعداد للمالك والمدير محسوبة من بيانات الفرع؛ تحرير ملف المطعم وبيانات اتصال الفرع مع نشر اختياري في منيو الضيف. دعوات موظفين بالبريد، برمز صالح 7 أيام وقبول مرة واحدة وإلغاء وحد باقة وسجل تدقيق؛ يلزم إعداد SMTP واختبار التسليم الفعلي قبل الإطلاق. تفعيل بريد المالك وإعداد العملة واستكمال جولة الإعداد مؤجلة. |
| الباقات | جزئي | تجربة 14 يومًا وحدود فروع وطاولات وأصناف وموظفين في خدمة مركزية، ومعاينة خفض الباقة للمالك عبر كل الفروع دون حذف بيانات، وتعليق المطعم بوضع قراءة فقط. تغيير الباقة يدوي من مشغل المنصة ويسري فور الحفظ. سجل تحصيل اشتراك يدوي بمرجع فريد وفترة ومبلغ بالجنيه المصري وهوية المشغل، مع عرض للمالك؛ لا يمدد الاشتراك تلقائيًا. فوترة آلية ومدفوعات إلكترونية وتجربة تزامن على PostgreSQL مؤجلة. |
| المنيو والطاولات | جزئي | تصنيفات مع إظهار/إخفاء، أصناف مع تعديل وتوفر، صور وأحجام بأسعار مستقلة، ومجموعات إضافات قابلة للتحرير مع حدود اختيار وخيارات أسعار وتوفر وترتيب وحذف آمن، وQR؛ استيراد CSV وXLSX بمعاينة واعتماد ذري وقواعد تحقق مشتركة. |
| طلب الضيف | منفذ للمسار الأساسي | سلة، تحقق خادمي، لقطة سعر، منع تكرار، متابعة حالة، ورمز جلسة طاولة يتغير عند إنهاء الخدمة دون تغيير QR. تحتاج اختبارات ضغط وتزامن إضافية. |
| شاشة المطبخ | جزئي | عرض وتحديث حالات وفحص اتصال واستعادة عبر polling كل 10 ثوانٍ، وتصفية حسب الحالة والطاولة والترتيب. حد تأخير قابل للضبط لكل فرع وعلامة تنبيه تتحول عند تجاوزه من وقت الخادم. محطات لكل فرع ضمن حد الباقة، وربط الصنف بمحطة مع حفظ توجيه سطر الطلب وحالات تحضير مستقلة لكل سطر مع سجل انتقالات، وتمنع جاهزية الطلب الموجّه قبل اكتمال جميع سطوره؛ الشاشة العامة تدير حالة الطلب كله وتظهر تنبيهًا للأصناف بلا محطة. الصوت وWebSocket واختبارات التزامن على PostgreSQL مؤجلة. |
| الخدمة والطلب التقليدي | جزئي | استدعاء الويتر والحساب وطلب موظف متعدد الأصناف والإضافات بنفس خدمة تسعير QR؛ إلغاء بسبب مسجل، وتعديل الطلب الجديد أو المستلم وغير المدفوع مع سجل نسخ قبل/بعد ومزامنة شاشة المطبخ. تصحيح حالة الطلب خطوة واحدة للخلف للمالك أو المدير بسبب مسجل، للطلبات الجارية غير المدفوعة فقط. تعديل عناصر الطلب بعد بدء التحضير غير مسموح حتى لو صُححت الحالة للخلف. حدود استجابة منفصلة للويتر والحساب لكل فرع، مع تنبيه داخل شاشة الخدمة عند التأخير؛ إشعارات التصعيد الخارجية مؤجلة. |
| التقارير وإدارة المنصة | جزئي | أعداد وقيمة الطلبات والتحصيل اليدوي وأكثر الأصناف ومتوسطات التشغيل مع أعداد العينات، وزمن تحضير الأصناف حسب المحطة من سجل انتقالات السطور، ونطاق تاريخ يطبق على CSV؛ لوحة مشغل للمطاعم والاشتراكات مع سبب وسجل تدقيق. تحرير الباقات داخل Django Admin يتطلب سببًا، والكيانات التشغيلية فيه للقراءة فقط. |
| صلابة الإنتاج | غير مكتمل | تحديد معدل الدخول واستعادة الحساب في قاعدة البيانات موجود؛ ما زالت مراقبة ونسخ احتياطي مجرّب واختبارات حمل ومراجعة أمنية وميدانية مطلوبة. |

## الخطوات التالية

1. اختبار تزامن حدود الباقات ومنع تكرار الطلبات على PostgreSQL تحت حمل حقيقي.
2. دراسة مسار الطلب الإضافي بعد بدء التحضير وتجربة تنسيق المحطات في مطعم فعلي.
3. إضافة قنوات تحديث لحظية عند تحديد استضافة مناسبة، مع إبقاء الاستعلام الدوري للاستعادة.
4. إضافة اختبارات واجهة للهاتف والتابلت والكمبيوتر واختبارات ضغط وعزل أوسع.
5. تشغيل تجربة مطعم فعلية ثم تثبيت التسعير والحدود وبيئة النشر.
