# تشغيل Serveza على السيرفر باستخدام Docker

هذا الإعداد لخادم Linux واحد، بخدمات PostgreSQL 16 وGunicorn وCaddy للـHTTPS وعامل للصيانة. يطبّق الترحيلات ويجمع الملفات الثابتة وينشئ مسؤول المنصة الأول تلقائيًا قبل استقبال الطلبات. لا يحتاج تثبيت Python أو PostgreSQL على السيرفر. يلزم Docker Engine وDocker Compose **2.30 أو أحدث** لدعم [ملفات البيئة بصيغة raw](https://docs.docker.com/compose/how-tos/environment-variables/set-environment-variables/)، وإنترنت لتنزيل الصور وبنائها.

## أول تشغيل — مرة واحدة

لتشغيل **أكثر من موقع على نفس السيرفر** اتبع [دليل المواقع المتعددة](DOCKER_MULTI_SITE.md) واستخدم بوابة HTTPS مشتركة. الخطوات التالية للوضع الفردي الذي يحجز 80/443 لنفسه.

1. ارفع ملفات المشروع إلى مجلد ثابت على السيرفر. وجّه سجل DNS للدومين إلى عنوان السيرفر، وافتح TCP 80 و443. يجب أن تكون هذه المنافذ متاحة لـCaddy، وألا تشير سجلات AAAA إلى سيرفر آخر. إذا توجد خدمة Nginx/Apache تستخدمها، يلزم تنسيق إعداد الوكيل قبل التشغيل. استخدم الدومين النهائي الذي ستبقي عليه روابط QR.
2. من مجلد المشروع، ولّد الإعداد الخاص بهذا السيرفر. استبدل الدومين والبريد في المثال:

```bash
docker run --rm -it --user "$(id -u):$(id -g)" -v "$PWD:/workspace" -w /workspace python:3.12-slim-bookworm python scripts/configure_docker.py --domain app.example.com --admin-email admin@example.com
```

يمكن تشغيل السكريبت مباشرة إذا كان Python متاحًا:

```bash
python3 scripts/configure_docker.py --domain app.example.com --admin-email admin@example.com
```

ينشئ `.env.docker` و`.docker-secrets/` بكلمات مرور عشوائية ومفتاح Django دائم. لا يعيد الكتابة فوق إعداد قائم، ولا يطبع كلمات المرور. احتفظ بنسخة مشفرة من الإعداد والأسرار خارج السيرفر؛ فقدانها لا يعالَج بإعادة التوليد. لا ترفعها إلى Git. على Linux مجلد الأسرار خاص بالمالك `0700`؛ الملفات داخله `0444` كي تقرأها خدمة التطبيق ذات UID 10001 عبر Compose secrets. لا تمنح الآخرين حق دخول المجلد. على Windows احمِ المجلد بصلاحيات NTFS أيضًا.

3. افتح `.env.docker` واضبط `DJANGO_EMAIL_HOST` و`DJANGO_EMAIL_HOST_USER` و`DJANGO_DEFAULT_FROM_EMAIL` حسب مزود SMTP. ضع كلمة مرور SMTP في `.docker-secrets/smtp_password` فقط. لتعديل الملف على Linux: `chmod 600 .docker-secrets/smtp_password`، عدّله بالمحرر، ثم `chmod 444 .docker-secrets/smtp_password`. عدّل المنفذ وTLS بحسب المزود؛ الإعداد يدعم SMTP مع STARTTLS. لا ترسل الأسرار في المحادثات. الموقع يبدأ دون إعداد البريد، لكن التسجيل والتفعيل والدعوات واستعادة كلمات المرور تحتاج SMTP صالحًا واختبار تسليم فعلي.
4. شغّل:

```bash
docker compose up -d --build --wait --wait-timeout 300
docker compose ps
```

افتح `https://app.example.com`. يصدر Caddy الشهادة ويجددها تلقائيًا إذا كانت DNS والمنافذ صحيحة. تسجيل دخول المسؤول من `/django-admin/` بالبريد المحدد وكلمة المرور المحفوظة في `.docker-secrets/admin_password`؛ غيّرها بعد الدخول. يمكنك استخدام `/platform/` لإدارة المنصة. إعادة تشغيل الخدمة لا تعيد كلمة المرور القديمة ولا ترقّي حسابًا عاديًا يحمل نفس البريد؛ التعارض يوقف البدء ويظهر في السجل.

## ما يُحفظ تلقائيًا

البيانات في `postgres_data`، الصور في `media_data`، الأصول في `static_data`، النسخ في `backups`، وشهادات Caddy في `caddy_data` و`caddy_config`. التطبيق يعمل كمستخدم غير root بملفات كود للقراءة فقط. قاعدة البيانات وGunicorn لا ينشران منافذ عامة؛ Caddy يتصل بالتطبيق عبر Unix socket ويستبدل عنوان العميل الموثوق، للحفاظ على تحديد معدل الطلبات. لا تضف منفذًا مباشرًا للتطبيق مع إبقاء الثقة بالوكيل.

احتفظ باسم مجلد المشروع/اسم Compose نفسه عند التحديث لأن أسماء الـvolumes تعتمد عليه. إذا استخدمت `-p` أو `COMPOSE_PROJECT_NAME`، استخدم نفس القيمة في **كل** الأوامر. `docker compose down` يحفظ البيانات؛ `down -v` يمسحها. تبديل كلمة مرور ملف PostgreSQL وحده لا يغيّر كلمة المرور داخل قاعدة قائمة: التدوير يحتاج تعديلًا منسقًا داخل PostgreSQL أيضًا.

العامل يشغّل تنظيف محاولات الدخول كل ساعة، وتنظيف الاستيراد وتجميع توصيات الأصناف وتنظيف أحداثها كل يوم. النسخ الاحتياطي يتطلب نافذة إيقاف للكتابة، وليس مهمة خلفية تلقائية. الإعداد مخصص لنسخة تطبيق واحدة وعامل واحد؛ لا تستخدم `--scale web` على هذا الإعداد لأن الترحيلات والتهيئة تتم عند البدء.

## نقل بيانات مشروع قائم

صورة Docker تحتوي الكود والأصول فقط. **رفع الكود لا ينقل SQLite أو PostgreSQL الحالي أو الصور.** أول تشغيل بقاعدة جديدة يبدأ بلا مطاعم أو طلبات قديمة. قبل نقل نظام قائم خذ نسخة بـ`backup_application`، واختبر استعادتها، وانقل القاعدة والصور والأسرار بصورة منفصلة قبل تحويل DNS. نسخة SQLite لا تُستورد مباشرة في PostgreSQL؛ تحتاج عملية تحويل بيانات واختبار منفصلة، وليست خطوة تلقائية في هذا الإعداد.

إذا لديك volume PostgreSQL 16 من Compose التطوير القديم، لا تشغّل عليه إعداد الإنتاج بكلمة مرور جديدة؛ ملف التهيئة لا يغيّر مستخدم قاعدة قائمة. احتفظ بالـvolume ونسخته واستعده في بيئة تجريبية أو نسّق تغيير كلمة المرور أولًا. لا تستخدم `down -v` لحل خطأ دخول.

احتفظ بقيم `qr_public_origin` ورموز الطاولات و`SITE_URL` النهائي وDNS للدومين المطبوع. لا تعِد إنشاء الطاولات أو تدوير QR عند النقل. تغيير الدومين دون استمرار خدمة روابطه القديمة يُعطّل الرموز المطبوعة.

## التشغيل والتحديث

```bash
docker compose logs --tail 100 web proxy scheduler
docker compose exec web python manage.py check --deploy
curl --fail https://app.example.com/health/
```

يُظهر `check --deploy` تحذيري HSTS الخاصة بالنطاقات الفرعية وpreload ما لم يُتخذ قرار تفعيلهما على الدومين الحقيقي. لا تغيّرهما فقط لإخفاء التحذير. لا تستخدم `curl -k` للتحقق من شهادة الدومين العام.

قبل تحديث الكود، خذ نسخة واختبرها. ارفع النسخة الجديدة ثم نفّذ `docker compose up -d --build --wait --wait-timeout 300`. البداية تُطبق الترحيلات قبل تشغيل Gunicorn، وفشلها يمنع خدمة الطلبات. لا يوجد تراجع تلقائي لترحيلات قاعدة البيانات؛ العودة إلى إصدار أقدم تحتاج تقييم توافق الترحيلات أو استعادة النسخة ضمن نافذة توقف. راقب السجلات بعد التحديث. عامل الصيانة ينتظر صحة التطبيق عند الإنشاء؛ الإيقاف والصيانة اليدويان يجب أن يشملاه أيضًا.

لإعادة تشغيل خدمات قائمة: `docker compose restart`. للإيقاف: `docker compose down` ثم نفس أمر التشغيل عند العودة. `restart: unless-stopped` يعيد الخدمات بعد إعادة تشغيل السيرفر إذا كانت تعمل قبله. فشل healthcheck وحده لا يعيد تشغيل الحاوية؛ أضف مراقبة وتنبيهًا خارجيًا.

## نسخة احتياطية قابلة للتحقق

اختر اسم ملف جديد في كل مرة، وأوقف أي أدوات أخرى تكتب إلى القاعدة:

```bash
docker compose stop web scheduler
docker compose run --rm --no-deps web python manage.py backup_application --output /backups/before-update-2026-11-28.zip
install -d -m 700 backups
docker compose cp web:/backups/before-update-2026-11-28.zip backups/
docker compose up -d --wait --wait-timeout 300
```

لا تترك النسخة الوحيدة داخل volume على السيرفر نفسه. انقل الملف إلى تخزين مستقل محمي. يتضمن الصور وPostgreSQL dump وmanifest مع hashes، ولا يتضمن ملفات الأسرار. للتحقق والاستخراج في مجلد جديد:

```bash
docker compose run --rm --no-deps web python manage.py restore_application_backup --source /backups/before-update-2026-11-28.zip --destination /backups/verified-2026-11-28
```

هذا الأمر يتحقق ويستخرج فقط، ولا يغيّر قاعدة التشغيل. استعد `database.dump` عبر `pg_restore --exit-on-error --no-owner --no-acl` إلى **قاعدة تجريبية جديدة**، واستعد `media/` وقارن عدد الصفوف بالـmanifest، ثم جرّب الدخول والطلبات وQR والصور قبل اعتماد خطة الاستعادة. عميل PostgreSQL 16 موجود في صورة التطبيق. راجع أيضًا [دليل النشر](DEPLOYMENT.md).

## التحقق والتطوير المحلي

أضيف اختبار بناء وتشغيل كامل في CI: `scripts/docker_smoke.py`. يفحص HTTPS محليًا، العربية RTL والإنجليزية LTR، تقديم الأصول والصور وحجب HTML المرفوع، استمرارية البيانات بعد إعادة إنشاء الحاويات، وثبات حساب المسؤول، والنسخ والاستعادة إلى PostgreSQL تجريبي. يتطلب اسم Compose مستقلًا يبدأ بـ`serveza-smoke-` وإعداد `--domain localhost --local --admin-email smoke@example.com`. يستخدم شهادة Caddy محلية مع تعطيل تحقق الثقة في هذا الاختبار فقط. **لا تشغّله على بيانات حقيقية**؛ ينشئ بيانات تجريبية ويوقف الخدمات. تنظيف CI للـvolumes يخص مشروع الاختبار المعزول فقط.

اجتازت الحزمة الأساسية 326 اختبارًا: 315 ناجحة و11 متخطاة لاحتياج PostgreSQL، ومنها الاختبارات الثمانية الجديدة للإعداد والتهيئة. نجحت فحوص Django واتساق الترحيلات وCompose 2.30.3 وCaddy 2.11.9، واختبار HTTP محلي لمسارات static والصور وحجب HTML وفهرس المجلدات. فحص إعداد الحاوية بـ`check --deploy` أظهر تحذيري HSTS المقصودين فقط. الأدلة المحلية في `tmp/docker-core.log` و`tmp/docker-validation/` (ملفات مؤقتة لا تُرفع).

Docker غير متوفر على جهاز التطوير الذي أُعدت عليه هذه الدفعة؛ نجاح هذه الفحوص لا يثبت نجاح البناء والحاويات أو شهادة الدومين أو تسليم البريد. اعتماد النشر يتطلب نجاح وظيفة Docker في CI ثم فحص الدومين والسيرفر الفعليين.

إعداد التطوير السابق موجود منفصلًا في `docker-compose.dev.yml`. استخدم اسم مشروع منفصلًا كي لا يشارك بيانات الإنتاج:

```bash
docker compose -p serveza-dev -f docker-compose.dev.yml up --build
```

هذا يشغّل `runserver` على المنفذ 8000 بإعداد تطوير وكلمة مرور قاعدة توضيحية؛ لا تستخدمه للسيرفر العام.
